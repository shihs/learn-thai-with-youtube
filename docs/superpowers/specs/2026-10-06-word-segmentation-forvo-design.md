# 單字拆解改進、詞庫與 Forvo 真人發音連結：設計

日期：2026-10-06

## 背景

單字解析目前由 `gpt-4.1-mini` 直接拆詞並解釋。掃過 `data/subtitles/` 的資料後有三個發現：

- **有些拆得太長**：2.9% 的單字長度在 10 個泰文字元以上，其中有整段字幕被當成一筆的（最長 39 個字元），也有 3–6 個詞的片語沒拆。原因是 schema 的 `word` 描述寫「泰文單字或片語」，prompt 沒有規定粒度，也沒有要求涵蓋整句。
- **大量重複**：14,469 筆單字解析只有 2,955 個不同的字，79.6% 是重複的，每次都重新請 GPT 產生。
- **同一個字前後不一致**：出現 5 次以上的字裡，只有 34% 每次拼音都寫得一樣。意思的差異則有一部分是真的一字多義（`ที่`、`แล้ว`），需要看上下文。

另外想在每張單字卡加上 Forvo 連結聽真人發音。Forvo 只收詞條，片語搜不到，所以拆詞要先修好。

## 目標

1. 單字解析以「字典詞條」為單位，照原句順序涵蓋每一個詞。
2. 已經解析過的字不再重新產生拼音、組成和一般說明，同一個字在所有影片裡一致。
3. 每張單字卡可以另開分頁到 Forvo 聽真人發音。

## 不做的事

- 不在頁面內直接播放 Forvo 錄音（需要付費 API）。
- 不自動批次重跑所有舊影片。
- 不修字幕本身的錯字。
- 畫面上不提供「有沒有 pythainlp」的選項，開關只在後端設定。
- 整句的拼音仍由 GPT 產生，不改成用詞庫的拼音拼接。
- 同形異音字不特別處理，以泰文拼法當詞庫的 key。

## 拆詞規則

單位是「字典詞條」：會是泰語字典裡一個詞條的東西就是一筆。

| 類型 | 例子 | 做法 | `type` |
|---|---|---|---|
| 一般單字 | `มา`、`สวย` | 一筆 | `word` |
| 複合詞 | `เครื่องเขียน`、`ตู้เย็น` | 整個一筆，組成放詞庫的 `parts` | `word` |
| 固定說法、慣用語 | `เป็นไงบ้าง`、`ไม่เป็นไร`、`ชี้เป็นชี้ตาย` | 整個一筆，組成放詞庫的 `parts` | `expression` |
| 語氣詞 | `ค่ะ`、`นะ`、`เลย` | 各自一筆，解釋功能 | `particle` |
| 量詞 | `คน`、`ตัว`、`อัน` | 各自一筆 | `classifier` |
| 疊字 | `เริ่มเริ่ม`、`ดอกๆ` | 一筆，說明原形與重複的效果 | `word` |
| 數字與時間 | `สองทุ่มครึ่ง` | 拆成 `สอง` / `ทุ่ม` / `ครึ่ง` | `word` |
| 人名、品牌、外文 | `บอนนี่`、`High School Frenemy` | 整個一筆，不拆 | `name` |
| 一般片語、子句 | `บอนนี่มีพี่น้องไหมคะ` | 一定要拆 | — |

跨詞的句型（`ไม่ค่อย…`、`…ไหม`、`กำลัง…อยู่`）不另外開一筆，寫在相關單字的本句補充裡。

## 資料怎麼分

每個字的資料分成兩種，來源不同：

| | 欄位 | 來源 |
|---|---|---|
| 隨句子變的 | `type`、`meaning`（在這句的意思）、`more`（這句特有的補充，沒有就空字串） | 每句送 GPT（第一步） |
| 不隨句子變的 | `rtgs`、`parts`、`senses`（常見意思）、`usage`（一般用法說明） | 詞庫，每個字只問 GPT 一次（第二步） |

`type` 放在句子這邊，因為同一個字在不同句子可能不同（`คน` 可以是名詞「人」，也可以是量詞）。

## 流程

```
字幕 ──► 第一步：逐句解析（GPT）──► 檢查 ──► 沒通過的重送一次
                                         │
                                         ▼
              第二步：找出詞庫沒有的字 ──► 查詞（GPT）──► 寫入詞庫
                                         │
                                         ▼
                        合併句子解析與詞庫 ──► 存成前端用的字幕檔
```

### 第一步：逐句解析

每 10 句一段、同時 5 段送出，和現在相同。

**送出的內容**由環境變數 `SEGMENT_HINT`（`on` / `off`，沒設定時是 `on`）決定：

- `on`：每句是 `{"thai": 原句, "tokens": [pythainlp 的切法]}`。
- `off`：每句是 `{"thai": 原句}`。

**prompt 規則**（取代原本的「逐字的文法解析」）：

- 以字典詞條為單位，照原句順序列出每一個詞，不能漏，也不能改字。
- 複合詞和固定說法整個一筆；語氣詞、量詞各自一筆；人名、品牌、外文整個一筆。
- 不可以把片語或子句當成一筆。
- `meaning` 寫這個字在這一句裡的意思，要簡短。
- `more` 只在這一句有特別的用法或句型時才寫，否則給空字串。
- （只在 `on` 時）`tokens` 是機器斷詞的參考，人名會被切碎、慣用語會被拆散，要自己合併修正。

原有的三條規則（每個 key 都要回傳、不合併或拆開句子、換行對應）保留。

**schema**：每句回 `rtgs`、`translation`、`analysis`；`analysis` 的每筆是 `word`、`type`、`meaning`、`more`，全部必填。`type` 是 `word`、`particle`、`classifier`、`name`、`expression` 五選一。

### 檢查：`check_analysis(thai, analysis) -> list[str]`

純函式，回傳沒通過的原因清單，空清單代表通過。不受 `SEGMENT_HINT` 影響，永遠用 pythainlp。

1. **涵蓋**：所有 `word` 照順序接起來，和原句各自只留下文字、聲調符號與數字（去掉空白、標點和音符這類符號）後要完全相等。只有符號的字幕配上空的單字清單算通過。
2. **粒度**：`type` 不是 `name` 的單字，用 pythainlp 斷詞後如果超過 4 個 token，視為沒拆好。

### 重送

分兩輪，共用同一個執行緒池：

1. 第一輪送出所有段。段內漏回的句子照現在的做法重送一次。每完成一段就存進快取，沒通過檢查的結果也先存。
2. 第一輪全部結束後，把全片沒通過檢查的句子各自當成一個請求，同時送出。
3. 重送的結果通過檢查就取代原結果；沒通過就保留第一輪的結果、加上 `"resent": true`，並印出句子 id 和原因。

每句最多重送一次：有 `resent` 的句子之後重跑不會再送。如果任務在第一輪和第二輪之間中斷，下次重跑時快取裡沒通過檢查、也還沒有 `resent` 的句子會補送。

### 第二步：詞庫

**詞庫檔**：`data/dictionary.json`，格式是 `{泰文單字: {"rtgs", "parts", "senses", "usage"}}`。

- `parts`：陣列，每個元素含 `word`、`rtgs`、`meaning`；不是複合詞或固定說法就是空陣列。
- `senses`：這個字常見的意思，可以有多個。
- `usage`：一般的用法說明。

`data/` 不進版本控制，所以詞庫只存在本機，隨著看過的影片累積。

**查詞**：

1. 第一步結束後，收集全片所有 `word`（包含從快取沿用的句子），去掉重複，找出詞庫裡沒有的。
2. 每 40 個字一批送 GPT，同時最多 5 批。每個字附上它第一次出現的那一句當參考，並要求說明這個字一般的用法，不要只針對那一句。
3. 每完成一批就寫入詞庫。失敗的批次重試一次。

**同時寫入**：兩支影片可能同時在跑。詞庫的寫入用一個全域鎖包住「讀檔 → 合併新字 → 寫檔」，已經存在的字不覆蓋。

### 合併與存檔

`long_analyze_and_save` 存字幕檔時，把每句的解析和詞庫合併，每筆單字變成：

```json
{
  "word": "เครื่องเขียน",
  "type": "word",
  "meaning": "文具",
  "more": "",
  "rtgs": "khrueang khian",
  "parts": [
    {"word": "เครื่อง", "rtgs": "khrueang", "meaning": "器具"},
    {"word": "เขียน", "rtgs": "khian", "meaning": "寫"}
  ],
  "senses": "文具",
  "usage": "…"
}
```

字幕檔自己就帶有完整資料，不用依賴詞庫檔，所以 repo 裡的範例字幕可以單獨使用。

如果查詞失敗，某個字在詞庫裡找不到：該筆的詞庫欄位留空，那一句的解析加上 `"partial": true`。

### 版本與快取

- `storage.py` 新增 `ANALYSIS_VERSION = 2`。第一步回傳的每句解析加上 `"v": ANALYSIS_VERSION`。
- `data/explanations/{id}.json` 只存第一步的結果。快取條件從「泰文相同」改成「泰文相同而且 `v` 等於目前版本」。
- `storage.is_subtitle_complete`：每一句有內容的字幕都有 `v` 等於目前版本、而且沒有 `partial` 的解析。
- `storage.list_subtitle_videos` 的 `explained` 用同樣的條件計算。

效果：

- 舊影片在清單上顯示為未完成。對某一支按「抓取字幕」才會重跑那一支，重跑前舊解析照常顯示。
- 有 `partial` 句子的影片再按一次「抓取字幕」，第一步會全部沿用快取，只補跑查詞。

### 任務進度

查詞期間任務狀態的 `stage` 是 `dictionary`，訊息是「建立詞庫中」，`done` / `total` 是已查的字數與要查的字數。任務結束時如果還有字查不到，訊息提示再按一次可以補上。

## 後端模組

| 檔案 | 責任 |
|---|---|
| `backend/segmenter.py`（新） | `tokenize(text) -> list[str]`：pythainlp `newmm` 斷詞，去掉純空白的 token |
| `backend/analysis_check.py`（新） | `check_analysis` |
| `backend/dictionary.py`（新） | 讀取詞庫、找出缺的字、加鎖寫入、把句子解析和詞庫合併 |
| `backend/gpt_teacher.py` | 兩種 GPT 請求（逐句解析、查詞）、`SEGMENT_HINT`、兩輪重送 |
| `backend/jobs.py` | 串起第一步、第二步、合併存檔，更新任務進度 |
| `backend/storage.py` | `ANALYSIS_VERSION`、詞庫檔路徑、完成度判斷 |

`requirements.txt` 加上 `pythainlp`（鎖定版本）。`newmm` 的字典隨套件附帶，不需要另外下載。套件約 62 MB，Docker 映像檔會變大。實作時要確認鎖定的版本在 Dockerfile 的 Python 3.10 上可以安裝。

pythainlp 的執行時間可以忽略：實測 554 句斷詞 0.07 秒、8,498 筆單字斷詞 0.09 秒，字典載入 0.3 秒且只發生一次。

## 前端（`frontend/src/VideoSubtitleApp.jsx`）

### 單字卡

由上到下：

1. **第一列**：單字與拼音靠左，Forvo 連結靠右；類型標籤接在拼音後面。
2. **`meaning`**：在這句的意思。
3. **組成**：`parts` 不是空陣列時顯示，列出每個組成的泰文、拼音和意思，用「+」隔開。每個組成的泰文是連到 Forvo 的連結。
4. **`more`**：這句特有的補充，有才顯示。
5. **`senses` 與 `usage`**：小字顯示。`senses` 和 `meaning` 相同時不重複顯示。

### Forvo 連結

- 新增 `forvoUrl(word)`，回傳 `https://forvo.com/search/${encodeURIComponent(word)}/`。
- 實作時測試 `https://forvo.com/search/<單字>/th/` 是否只顯示泰語結果；可以的話改用這個格式。
- 用 `<a target="_blank" rel="noopener noreferrer">`，圖示是 lucide 的 `Headphones`，樣式沿用 `iconButtonClass`。
- `title` 與 `aria-label`：「在 Forvo 聽真人發音（另開分頁）」。
- 圖示常駐顯示。`type` 是 `name` 的單字不顯示。

不用 `Volume2`，因為它已經是「AI 唸這句」。

### 類型標籤

`particle` 顯示「語氣詞」、`classifier` 顯示「量詞」、`name` 顯示「專有名詞」、`expression` 顯示「固定說法」。`word` 不顯示標籤。

### 相容舊資料

舊解析只有 `word`、`rtgs`、`meaning`、`more`。沒有 `type` 時當成 `word`，沒有 `parts`、`senses`、`usage` 時不顯示對應的那幾行。

## 對照實驗

目的是決定 `SEGMENT_HINT` 的預設值，並量出新流程的速度與用量。

- **素材**：`7tMkVWSWePg` 全部（43 句），加上 `muCvDSOJwSs` 的前 60 句（這支過長的單字最多）。
- **三組**：舊版（`main` 的程式）、新版 `on`、新版 `off`。每組都從空的暫存詞庫開始，結果寫到暫存目錄，不動 `data/`。
- **比較的數字**：
  - 第一輪檢查沒通過的句數（舊版也用同一個 `check_analysis` 量）。
  - 重送後仍沒通過的句數。
  - 長度 10 個字元以上的單字比例。
  - 耗時與 token 用量，第一步和第二步分開記。第一步的數字代表詞庫已經建好之後的成本。
- **判斷**：`on` 在「重送後仍沒通過的句數」上比 `off` 少就預設 `on`；相同或比較多就預設 `off`。

這一步會用到 OpenAI 金鑰並產生費用，執行前要先取得同意。

不論結果如何，pythainlp 都會保留，因為檢查需要它。

## 測試

新增 pytest（放在 `requirements-dev.txt`），測試檔放在 `tests/`。只測純邏輯，不呼叫 OpenAI。

- **`check_analysis`**
  - 涵蓋：完整涵蓋通過；漏詞、改字、順序錯都不通過；空白、標點與符號的差異不影響。
  - 粒度：`พร้อมที่จะส่งเราให้ไปแบบใช่กันไปเรื่อยๆ` 當成一筆不通過；`เครื่องเขียน`、`ชี้เป็นชี้ตาย` 通過；`type` 是 `name` 的長姓名通過。
- **詞庫**
  - 找出缺的字：去掉重複、排除詞庫已有的。
  - 寫入：已經存在的字不被覆蓋；寫入後重新讀取內容一致。
  - 合併：詞庫有的字帶入詞庫欄位；詞庫沒有的字欄位留空，而且該句被標成 `partial`。
- **快取與完成度**
  - 沒有 `v` 或 `v` 不同的解析不會被沿用。
  - 含舊版解析或 `partial` 句子的字幕檔，`is_subtitle_complete` 回傳 `False`。
- **`segmenter.tokenize`**：回傳字串清單，不含純空白的 token。
- **prompt 組裝**：`SEGMENT_HINT=off` 時送出的內容不含 `tokens`。

GPT 實際的拆詞品質用對照實驗的數字衡量。前端沒有測試框架，實際開頁面檢查：新資料的連結、標籤、組成；舊資料正常顯示；深色模式與手機寬度。
